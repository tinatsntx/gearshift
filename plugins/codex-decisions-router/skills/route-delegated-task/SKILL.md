# Route delegated coding work

This is host-invoked guidance, not middleware that intercepts every delegation. The MCP tool only recommends settings. It does not execute tasks, change permissions, or prove model access. Live mode can make one paid external classification request after separate user authorization and trusted startup configuration. Default mode is offline.

## Before routing

1. Honor the user's explicit model/effort and governing organizational/project policy first. A compatible explicit pin bypasses classification, including max/ultra settings outside the automatic presets. If a pin is incompatible, report the conflict rather than substituting.
2. Inspect the current native child tool's actual schema. It must support applying both model and reasoning effort. Do not invent tool names or arguments. If it lacks this capability, explain that automatic application is unsupported. A recommendation cannot change the parent model.
3. Use the effective native host catalog when available. A CLI app-server catalog from a different profile/provider may not match this host. A listed model is advertised, not necessarily entitled. Use supported efforts/modalities exactly as observed; mark unknown context/tool compatibility honestly. Do not invent a context window or inspect credentials.
4. Avoid a custom agent configuration that overrides the pair. If the user deliberately pinned that agent, honor it. Never rewrite agent files to force routing.
5. If overrides require a fresh/bounded-history child, use that supported path. Do not silently change an explicit full-history requirement. Surface a genuine host incompatibility.

## Minimal routing input

Infer only these seven feature buckets from the already-visible delegation contract. Unknown is valid; do not run another model, repository scan, or dependency analysis just to route.

- task_kind: inspect, mechanical_edit, implement, debug, review, design, unknown
- scope: localized, multi_component, cross_system, unknown
- uncertainty: specified_solution, reproducible_problem, open_investigation, unknown
- consequence: low_reversible, consequential, critical, unknown
- verification: executable_acceptance, partial_checks, human_only, unknown
- urgency: interactive, standard, background, unknown
- prior_failure: none, quality_failure, environment_blocker, access_or_transport, unknown

Call the discovered route_task tool once with its exact schema. Provide the host's effective catalog, readiness, required modalities and access state. Include privacy (non_sensitive, sensitive, phi, unknown); anything except non_sensitive stays local. optimization_goal defaults to balanced; quality/economy require explicit user/project policy. Do not send task text, code, diff, history, file/repository names, paths, identities, images, secrets, or PHI. Do not pass endpoints, keys, provider prompts, timeouts, shell commands or policy overrides. Features do not grant authorization.

## Apply only usable recommendations

- Never launch real work using source=fixture. It is simulation only, including cached fixture selections
- blocked/unsupported or selected=null means stop automatic delegation and report the fixed reason
- A refusal or access/policy denial stops the flow. Do not ask a stronger model, another provider or identity to bypass it
- A recommended/fallback selection with a real host catalog can request both returned settings on the original native delegated task, within the original authorization, sandbox and permissions
- Preserve the task and its scope. Do not execute provider output as commands or create demonstration work
- Record recommendation, requested settings and effective application separately. Tool-call parameters show requested settings; effective child runtime metadata is stronger evidence. If absent, application is unverified. The router always returns applied=false
- Do not recursively route the same delegation

A timeout means the local routing wait ended. The external classification may still have been processed/billed. No coding task is started by this tool.

## Bounded recovery

There are zero foreground HTTP retries. Local fallback obeys the same compatibility/risk/allowlist limits. Environment, authentication, network and permission blockers do not justify a model upgrade. If a child has already started or may have made changes, never duplicate it blindly.

Only after the host confirms a genuine quality failure may it route at most one escalation with attempt=1, prior_failure=quality_failure and previous_preset set to the original preset. Higher tiers are application priors, not proven rankings. A rejected setting before work starts may allow one catalog-refresh/fallback spawn attempt within the original authorized task; remove the rejected pair and stop if rejection persists. This is distinct from repeating classification after a denial/refusal. The host owns attempt state; do not reset it to evade the ceiling.
